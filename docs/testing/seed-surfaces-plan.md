| Bridge — **pinned to an exact version, resolved offline** | The pool spawns `npx --yes wicked-interactive@^0.8.1 serve --root <root>` **detached** under the scratch HOME. `Rig.pin_bridge` (a) finds the operator's already-resolved `~/.npm/_npx/<hash>` install for exactly that spec, reads the INSTALLED `wicked-interactive` version and the tarball integrity (sha512) from the cache's own lockfile, and requires version == **`BRIDGE_PINNED_VERSION` = `0.8.1`**; (b) CLONES it (APFS clonefile; read-only on the source) into the scratch npm cache under the same key and re-reads the clone's version; (c) seeds the operator's CACHED registry manifest for `wicked-interactive` (the cacache `request-cache` index entry + content blob, same layout) into the scratch cache and proves that the `^0.8.1` range resolves to the pin FROM THAT FROZEN SNAPSHOT (`caret_max`: `^0.8.1` = ≥0.8.1 <0.9.0 — the manifest cached 2026-09-09 lists 0.9.0 as `latest`, which the caret excludes); (d) the daemon's env carries **`npm_config_offline=true`**, so npx can only use the seeded manifest + the clone — a cache miss is a loud bridge-start failure, never a registry resolution (an `--offline` run WITHOUT the seeded manifest fails `ENOTCACHED`; npx resolves the range against the manifest even with a warm `_npx` install). **Revision 8 — the pin is BYTES, not a label (codex r4 #4):** `resolve_bridge_pin` VALIDATES the lock metadata — the installed `package.json`, the root `package-lock.json` entry AND npm's hidden lockfile (`node_modules/.package-lock.json`, written after npm verified the extracted tarball) must all name 0.8.1; the integrity must be a well-formed `sha512-<86 base64>==` (`INTEGRITY_RE`) and identical in both lockfiles — a lock naming `9.9.9`, an `integrity: "not-an-integrity"`, a missing or disagreeing hidden lockfile is a setup failure. After the clone, `verify_bridge_clone` (e) walks the clone with `lstat` and REFUSES any symlink whose target escapes the clone (npm's `.bin` shims are relative links inside `node_modules`; an absolute or `..`-escaping target fails), **(e′, revision 9 — codex r5 #2) compares every symlink BY `readlink` TARGET, source vs clone** — a link missing, added or RETARGETED (the `.bin/wicked-interactive` shim pointed at another internal file, which no file hash can see) is an error, and `clone_tree_sha256` covers the targets; (f) hashes every regular file of the clone (sha256) and requires byte-equality with the source install — nothing missing, extra or mismatched (11,316 files on this host), and (g) ties the package to the recorded integrity ONLY where trusted bytes exist: when the operator's cacache still holds the tarball blob for that integrity (`content-v2/sha512/<hex>`), the blob's sha512 must equal the integrity and every `package/` member must be byte-equal to the clone's `node_modules/wicked-interactive` — `bytes_authenticated: true`. **When it does not (npx does not retain tarballs after extraction — the case on this host), NOTHING on the host authenticates the package bytes against that sha512**: npm's lockfiles record the tarball digest but no per-file digest, and nothing records the lockfiles' own integrity — so revision 9 records that route as `bytes_verified_by: "lockfile-metadata (unauthenticated): …"` with `bytes_authenticated: false` (revision 8 had called it a "hidden lockfile" verification — the overclaim codex r5 #2 named). What IS proven on this host: the clone is the source install (every file, every symlink target, no escape — `clone_equals_source: true`) and npm's metadata is self-consistent; what is NOT: that the source install's bytes are the registry tarball's. `setup.bridge.clone_verification.{bytes_verified_by, bytes_authenticated, clone_equals_source, symlinks_retargeted, symlinks_missing_in_clone, symlinks_extra_in_clone, …}` state exactly this; `package_tree_sha256` / `clone_tree_sha256` record the digests. Everything lands in `setup.bridge` = `{pinned, version, lock_version, integrity, hidden_lock_integrity, resolved, path, scratch_path, cloned_version, clone_verification{files_compared, symlinks, symlinks_compared_by_target, symlinks_retargeted, escaping_symlinks, mismatched_count, tarball{present, …}, bytes_verified_by, bytes_authenticated, clone_equals_source}, registry_manifest{versions, dist_tags, cached_at, resolves_to}}`. No cache, a version drift, a lock naming another version, a malformed or disagreeing integrity, an escaping symlink, a byte mismatch, a manifest that resolves elsewhere, or a failed clone is a **setup failure** (`report.ok=false`, step `bridge_pin`). At teardown the identified bridge must have run FROM the scratch clone, the clone must still be 0.8.1, the bridge's lock must self-report 0.8.1, and the scratch cache must have gained NO content blob — otherwise `bridge_not_from_pinned_cache` fails the verdict (revision 9, codex r5 #1: these are inspected AFTER the identified pids were signalled; an unreadable or `null` `package.json`, or any raise inside the inspection, is recorded as `not_from_pinned_cache` — never a skipped terminate). **Why the pin matters:** 0.8.1 has no `DELETE /api/docs/:doc`; that is exactly the studio#213 expected gap the delete rows assert (CLN-1a–d, ISO-D, ISO-DD). A different bridge would flip those rows (to xpass, or to a crew#472 leak) — the results describe THIS bridge, by bytes. **Revision 11 (codex r6 #1, #3):** (h) `clone_root_containment` runs BEFORE any read — the clone ROOT and every ancestor strictly under the scratch dir are `lstat`ed (a symlink anywhere on that chain is an error: a copied cache-root link would resolve straight back into the operator's cache while the descendant walk sees "zero symlinks"), and the root's realpath must lie inside the scratch dir's realpath (`setup.bridge.clone_verification.root_containment`; a refusal records `clone_equals_source: false`, `bytes_authenticated: false`, no `files_compared`); (i) the tarball route is COMPLETE — the tarball's file SET must equal the clone's package file set in BOTH directions (an installed file the tarball does not carry is `members_extra_in_clone`), symlink members are compared by target (`symlinks_missing_in_clone` / `symlinks_extra_in_clone` / `symlinks_retargeted`), a hard link or special member is `members_unsupported` — and `bytes_authenticated` is ALWAYS stated (true only for a present tarball with no difference of any kind). |
